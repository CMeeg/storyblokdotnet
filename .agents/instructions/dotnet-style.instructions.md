# C# and .NET conventions

## Style and formatting

- Treat `.editorconfig` as the source of truth for formatting and code style.
- When `.editorconfig` leaves room for judgment, follow the conventions already used in existing source files.
  - Use file-scoped namespaces in C# files.
  - Use Allman braces.
  - Keep `using` directives outside the namespace and place `System` usings first.
  - Prefer explicit types over `var` unless the type is immediately obvious and readability improves.

## Solution and project structure

- Preserve the existing package layout: production code in `packages/{RootNamespace}.{PackageName}` and tests in `packages/{RootNamespace}.{PackageName}.Tests`.

## Package management

- Use the `nuget-manager` skill when working with NuGet packages in this repository.
- New NuGet dependencies should be added with central package management in `Directory.Packages.props`.
- Keep shared build and package metadata for projects in this repository in `Directory.Build.props`.
- Do not add NuGet package versions directly in project files unless the repository already has a documented exception.

## Naming conventions

- Interface names should be prefixed with an uppercase `I`.
- In this repository, do not add the `Async` suffix to method names by default, even for `Task`-returning methods. Only use it when required for compatibility with an external API or to avoid an unavoidable overload conflict.
- Keep names consistent; pick one style (e.g., `WithHostPort` or `WithBrowserPort`) and stick to it.
- Keep private and internal fields in camelCase and const fields in PascalCase.

## Code design rules

- Don't wrap existing abstractions.
- Don't default to `public`. Least-exposure rule: `private` > `internal` > `protected` > `public`
- Don't edit auto-generated code (`/api/*.cs`, `*.g.cs`, `// <auto-generated>`).
- Don't add unused methods/params.
- Don't add unused using statements.
- When fixing one method, check siblings for the same issue.
- Reuse existing methods as much as possible
- Move user-facing strings (e.g., AnalyzeAndConfirmNuGetConfigChanges) into resource files. Keep error/help text localizable.
- Prefer records to classes for DTOs
- Declare variables non-nullable, and check for `null` at entry points.
- Always use `is null` or `is not null` instead of `== null` or `!= null`.
- Trust the C# null annotations and don't add null checks when the type system says a value cannot be null.
- Use pattern matching and switch expressions wherever possible.
- Use `nameof` instead of string literals when referring to member names.

## Error Handling & Edge Cases

- **Null checks**: use `ArgumentNullException.ThrowIfNull(x)`; for strings use `string.IsNullOrWhiteSpace(x)`; guard early. Avoid blanket `!`.
- **Exceptions**: choose precise types (e.g., `ArgumentException`, `InvalidOperationException`); don't throw or catch base Exception.
- **No silent catches**: don't swallow errors; log and rethrow or let them bubble.

## Goals

### Productivity

- Prefer modern C# (file-scoped ns, raw """ strings, switch expr, ranges/indices, async streams) when TFM allows.
- Keep diffs small; reuse code; avoid new layers unless needed.
- Be IDE-friendly (go-to-def, rename, quick fixes work).

### Production ready

- Build warnings should be fixed, not ignored, unless there is a good reason to ignore them in which case that should be documented next where the exclusion appears.
- Secure by default (no secrets; input validate; least privilege).
- Resilient I/O (timeouts; retry with backoff when it fits).
- Structured logging with scopes; useful context; no log spam.
- Use precise exceptions; don’t swallow; keep cause/context.

### Performance

- Simple first; optimize hot paths when measured.
- Stream large payloads; avoid extra allocs.
- Use Span/Memory/pooling when it matters.

### Cloud-native / cloud-ready

- Cross-platform; guard OS-specific APIs.
- Diagnostics: health/ready when it fits; metrics + traces.
- Observability: ILogger + OpenTelemetry hooks.
- 12-factor: config from env; avoid stateful singletons.

## Testing

### Test structure

- When adding tests, place xUnit v3 test classes under `packages/{RootNamespace}.{PackageName}.Tests` with public test classes and `[Fact]` or `[Theory]` methods so `dotnet test` can discover them.
  - No class attribute; use `[Fact]`
  - Parameterized tests: `[Theory]` with `[InlineData]`
  - Setup/teardown: constructor and `IDisposable`
- Keep test classes public.
- Organize tests by system under test: keep each production type's tests in a dedicated file (for example, if the SUT is in a file named `MyHttpClientFactory.cs` then test should be in `MyHttpClientFactoryTests.cs` and test for `MyServiceCollectionExtensions` in `MyServiceCollectionExtensionsTests.cs`) instead of combining unrelated test groups in one file.
  - Folders and namespaces should mimic the SUT also.

### Naming conventions

- Name test methods using a concise underscore-separated `Subject_With_ExpectedResult` style where `Subject` is usually the method under test, `With` is a brief summation of the arguments or context used, and `ExpectedResult` is a brief summation of the expected result or primary assertion (for example, `Create_WithoutOptions_UsesEuDefaults`).

### Test design rules

- Follow the Arrange-Act-Assert (AAA) pattern
- Prefer multiple tests to multiple assertions in one test method.
- Tests should be able to run in any order or in parallel.
- Avoid disk I/O; if needed, randomize paths, don't clean up, log file locations.
- Test through **public APIs**; don't change visibility; avoid `InternalsVisibleTo` if possible.
- Require tests for new/changed **public APIs**.
- Assert specific values and edge cases, not vague outcomes.

## Mocking

- Avoid mocks/Fakes if possible
- External dependencies can be mocked. Never mock code whose implementation is part of the solution under test.
- If a external Mock/Fake library is required, check if one is already being used and use that; otherwise as for user feedback which library should be used.
